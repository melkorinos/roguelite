Introduce an OpponentProvider seam

Strong ports & adapters

hardcoded tier filter + element pool per round
No way to inject a backend-fetched or day-seeded opponent — generation is buried with no seam.

After

OpponentProvider.get_opponent(context) → Array
LocalDaySeeded
(now)
BackendHTTP

Problem. BattleSystem.create_opponent_grid(round_num) generates opponents locally from a hardcoded tier pool. The opponent source is fused into the system with no seam — a backend-fetched or day-seeded snapshot cannot be injected.

Solution. Extract an OpponentProvider module. PhaseSystem.to_battle() calls it; today's adapter generates a deterministic grid seeded by hash(OS.get_date_string_from_system()) (day-stable, same opponent for every player on a given day); tomorrow's adapter fetches via HTTP.

  • → leverage: one seam, two adapters — local and remote share the same interface
  • → locality: opponent generation concentrates in one module; PhaseSystem stays clean
  • → tests: inject a fixed grid without mocking BattleSystem internals
  • → unblocks async PvP with zero changes to PhaseSystem when backend lands
Build now: LocalDaySeededAdapter using hash(OS.get_date_string_from_system()) as the RNG seed. One opponent per calendar day, consistent for all players — this is the async PvP experience until a server exists.

Problem. advance_round() updates wins, lives, and phase but emits no event. tick_battle() accumulates battle_stats but nothing persists them across matches. Both are the natural places to fire Steam achievements or update a PlayerProfile — neither has a seam.

Solution. A pure AchievementSystem.check(state, profile) called by advance_round() after state is updated. It reads conditions from state, updates PlayerProfile, and calls PlatformLayer.set_achievement(). No mutation of game state.

  • → locality: all achievement conditions in one module, not scattered across PhaseSystem and BattleSystem
  • → leverage: one interface covers Steam achievements and internal milestones
  • → can be built now: stub the Steam call — zero backend dependency
Steam achievements wireable immediately: first win (wins == 1), first forge (len(discovered_recipes) == 1), win at 1 Life remaining (lives == 1 and result == "player_wins"), hard loss survived (lives_lost == 3 and lives > 0).

PlayerProfile autoload — cross-match persistence

Strong in-process

Before — match-scoped only

GameState.create() resets everything:
phase · round · gold · inventory
battle_grid · shop_items · lives
wins · forge_slots · battle_stats…
No cross-match data exists anywhere.
total_damage_ever · matches_won_ever

After — two scopes

GameState — match scope (unchanged)

total_damage: int
matches_won: int
achievements: Array[String]
milestones: Dictionary
discovered_recipes: Array[String]
Steam Cloud Save (adapter — later)

Problem. GameState is match-scoped and resets on GameState.create(). There is no cross-match persistence layer. Steam achievements requiring lifetime totals (e.g. "deal 20,000 damage") have nowhere to accumulate. The meta-progression layer has no stable player record to gate content against.

Solution. Add a PlayerProfile Autoload — same pattern as SettingsManager — persisting to user://profile.cfg. AchievementSystem reads and writes through it. Steam Cloud Save is a future adapter behind the same seam.

  • → locality: all cross-match data in one place; GameState stays clean
  • → leverage: serves achievements, milestones, meta-progression, and Steam Cloud Save from one interface
  • → can be built now: plain ConfigFile read/write, zero backend dependency

PlatformLayer — isolate GodotSteam from game code

Worth exploring ports & adapters

No game code ever calls Steam.*

Proposed

PlatformLayer autoload

clear_achievement(id) · store_stats()
is_steam_active() → bool
SteamAdapter
(calls GodotSteam)
NoOpAdapter
(web / headless)

Problem. GodotSteam is present in project.godot but no game code touches it. Naively scattering Steam.* calls through AchievementSystem will break web exports — GodotSteam requires a custom engine build incompatible with the web target. Two export targets are both in scope (Steam desktop + web).

Solution. A PlatformLayer autoload detects platform at startup. On Steam desktop it initialises GodotSteam and delegates SDK calls; on web (or any non-Steam build) it silently no-ops. AchievementSystem calls PlatformLayer.set_achievement(id) — never Steam.* directly.

  • → leverage: one module owns all platform SDK knowledge; everything else is platform-agnostic
  • → locality: swap or disable Steam without touching AchievementSystem or PlayerProfile
  • → two adapters justify the seam: Steam desktop + web export are both targeted (per project memory)

Expand the Opponent Snapshot shape in GameState

Worth exploring in-process

data/GameState.gd · systems/BattleSystem.gd · systems/PhaseSystem.gd

Current — four flat anonymous fields

opponent_grid: Array
opponent_timers: Array[float]
opponent_hp: int
opponent_starting_hp: int
# no identity, no source, no context

Backend fetch has nowhere to land. Battle.gd cannot show opponent name or source.

Proposed — one Opponent Snapshot dict

opponent_snapshot: {
  "player_id": String,  # "" = local
  "player_name": String,
  "round": int,
  "grid": Array,
  "acquired_day": int, # Unix day
  "source": String,   # "local"|"remote"
}

BattleSystem reads ["grid"] — no other changes when backend lands.

Problem. Flat opponent fields are anonymous — no shape for "who was this opponent, where did their Composition come from, when was it acquired?" When a backend arrives these fields need a home in state before any UI can show opponent name or attribution.

Solution. Collapse flat opponent fields into one opponent_snapshot Dictionary with a defined shape. source: "local" for today's generated grids; source: "remote" when backend-fetched. Battle.gd can show opponent_name immediately — even "Opponent #4" from the local adapter — and the shape is ready for the backend with no further GameState changes.

  • → locality: all opponent context in one dictionary key instead of four flat fields
  • → leverage: UI, AchievementSystem, and OpponentProvider all read the same shape

Top recommendation

Start with OpponentProvider + PlayerProfile in parallel

These two seams unblock everything else. OpponentProvider (Candidate 1) ships a coherent "fight today's opponent" experience today — using a day-seeded local adapter, zero backend required. When the backend arrives, swap the adapter without touching PhaseSystem or BattleSystem.

PlayerProfile (Candidate 3) is the foundation under both Steam achievements and future milestones. Without it, AchievementSystem has nowhere to accumulate lifetime totals, and Steam Cloud Save has nothing to sync. It follows the existing SettingsManager pattern — low implementation cost, high leverage.

Documented for future sessions

Internal Milestones — not in scope this session

Milestones are in-game achievements separate from Steam — e.g. "You dealt 20,000 damage." They share the PlayerProfile and AchievementSystem infrastructure but surface inside the game's meta-progression layer (unlocking Factions, Synergies, or run modifiers) rather than the Steam overlay. The distinction: Milestones are internal rewards that change what the player can build; Steam achievements are external recognition of the same events. Both flow through the same seam — build it once, wire both outputs.
