After — three Godot patterns compared

Option A — constants class UIScale.gd one file, no runtime cost 
class_name UIScale
const SHOP_EMOJI  := 50
const COMP_HEADER := 25
…
# call site unchanged, literal gone:
_lbl.add_theme_font_size_override("font_size", UIScale.SHOP_EMOJI)

Locality: one grep finds every usage. Still 25 call sites; only the literal disappears.

Option C — constants + static helper (recommended now) seam for future swap 
class_name UIScale
const SHOP_EMOJI := 50
static func apply(node: Control, size: int) -> void:
    node.add_theme_font_size_override("font_size", size)

# call site:
UIScale.apply(_emoji_lbl, UIScale.SHOP_EMOJI)

Leverage: call sites never change when Option B is adopted later — swap only the helper body.

Option B — Godot Theme type variations (right answer, future state) no override calls at all 
# Create res://ui_theme.tres in Godot editor
# Define "ShopTile" variation (inherits Label), font_size=50

# call site:
_emoji_lbl.theme_type_variation = "ShopTile"
# — no add_theme_font_size_override needed —

Depth: the size lives in the theme file, not in code. Change once, every node updates. But: every programmatic node (Compendium cards, Battle summary rows) still needs the variation string set on construction.

Problem

The size for each UI role is implicit — discoverable only by reading 8 different implementations. No interface, no seam; a global size change requires 25 edits.

Solution

Option C now. Option B after Sprint 2 when scene layouts stop moving. Option C's UIScale.apply() is the seam that makes that migration zero-cost at call sites.

Wins

  • → locality: all role sizes in one file
  • → leverage: one constant, N call sites
  • → seam created: swap implementation without touching callers
  • → grep-friendly: UIScale.SHOP_EMOJI shows all usage

Godot pattern note

Godot's canonical answer for this is Option B (Theme type variations). It is the correct architecture once the UI is stable enough to name its roles. The tradeoff right now is that your scenes are rewritten frequently — two full scene rewrites today alone. Option B adds friction (open .tres, define variation, add to project theme) on each new component. Option C is the Godot-compatible intermediate: it respects the add_theme_font_size_override method as the official way to deviate from the project default, and puts a named constant behind it.

One architectural fact worth knowing: for nodes built fully in GDScript (your Compendium cards, Battle summary rows), Option B also requires you to set theme_type_variation = "MyVariant" on each dynamically created node — it doesn't auto-apply to code-built nodes. This means Option B doesn't remove the per-node assignment; it changes what that assignment does.

Problem

Six state transformations live in the scene script, bypassing the system layer. They can't be tested without constructing the Godot scene tree. Bugs in forge-slot placement or grid-swapping have no test surface.

Solution

Move _swap_inv_to_grid, _swap_within_grid, _swap_grid_to_inv, and the three forge-slot handlers into ShopSystem.gd as static functions. Shop.gd becomes a thin signal dispatcher only.

Wins

  • → locality: all Shop-phase state logic in ShopSystem
  • → leverage: testable without scene tree
  • → enforces stated architecture rule (CLAUDE.md)
  • → Shop.gd shrinks by ~100 lines

3 — Drag payload is an undeclared Dictionary interface

Worth exploring

scenes/ShopItemTile.gd · scenes/InventorySlot.gd · scenes/BattleSlot.gd · scenes/ForgeSlot.gd · scenes/SellZone.gd

Before — implicit contract

{"type": "inventory", "slot": N}
{"type": "shop", "element_id": X, "price": P, "shop_slot": N}
{"type": "grid", "slot": N}

Checked by string comparison in 5 files. Rename "slot" → crash. No compile-time check. Every sender and every receiver must know the undocumented schema.

After — declared via class_name

class_name DragPayload

static func inventory(slot: int) -> Dictionary:
    return {"type": "inventory", "slot": slot}

static func shop(id: String, price: int, shop_slot: int) -> Dictionary:
    return {"type": "shop", "element_id": id,
            "price": price, "shop_slot": shop_slot}

static func grid(slot: int) -> Dictionary:
    return {"type": "grid", "slot": slot}

Senders call DragPayload.inventory(slot_index). One grep finds all payload construction sites.

Problem

The drag-and-drop contract is an undeclared interface — shape is only discoverable by reading all senders and receivers. Renaming a key requires grepping across 5 files with no compiler safety net.

Solution

A DragPayload module with one static factory per drag type. The schema is declared once; senders use the factories; receivers trust the shape.

Wins

  • → locality: payload schema in one file
  • → one grep finds all payload construction
  • → rename-safe: change factory, callers update cleanly

4 — _first_empty_slot duplicated across two systems

Speculative

systems/ShopSystem.gd:123 · systems/ForgeSystem.gd:142

Problem

Identical helper function (_first_empty_slot / _first_empty_inv_slot) in two separate system modules. Different names, same logic.

Solution

Move to GameState.gd as static func first_empty_slot(inv: Array) → int. Both systems call GameState.first_empty_slot(…).

Wins

  • → locality: one place if behaviour changes
  • → trivial change, zero risk

Top recommendation

If you can only do one thing, do Candidate 2 (move the 6 in-scene state mutations into ShopSystem). It restores the architecture rule your project already committed to, and it makes the shop-phase logic testable without a scene tree.

For the font question specifically: Option C now, Option B later. Godot's canonical answer is Theme type variations (Option B) — it eliminates every add_theme_font_size_override call in favour of one assigned variation string per node. But it requires the UI to be stable enough to name its roles. Your UI had two full scene rewrites today. Option C is the right intermediate: it centralises the values, creates the seam Option B needs, and costs you nothing when you're ready to migrate.
