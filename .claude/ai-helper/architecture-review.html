Problem. Phase transitions — shop → battle → result → shop — are not owned by any module. Each scene writes directly to GameManager.state["phase"] and resets whatever state keys it happens to know about. Callers must learn the full set of keys that accompany each transition; that knowledge is the interface, and it lives spread across three scene scripts.

Solution. A PhaseSystem module exposes to_battle(state), advance_round(state), to_result(state) — pure functions that own all resets. Scenes call one function and re-render.

  • → locality: all valid transitions live in one module; add a new phase in one file
  • → leverage: scenes shrink — no knowledge of which keys each transition resets
  • → interface is the test surface: state machine can be unit-tested without spinning up scenes
  • → delete 6 direct mutations from Battle.gd and 1 from Shop.gd

Problem. BattleSystem exposes get_player_stats(inventory) and reads damage/cooldown from ElementData, but none of it affects combat — the only damage event is a hardcoded sandstorm at 10 s. The interface is nearly as complex as the implementation; the unused surface is dead weight every caller and reader must account for.

Solution. Two honest paths: (a) delete get_player_stats and the cooldown field on every element until real ability-chain combat is implemented — makes the interface match the reality; or (b) implement discrete-tick simulation so damage and cooldown actually drive tick_battle — deepens the module significantly.

  • → interface shrinks with path (a): unused function and dead fields removed
  • → leverage grows with path (b): one module computes deterministic combat, tests verify outcomes without scenes
  • → deletion test: deleting get_player_stats today costs nothing — it's not earning its keep
Design note — the memory doc confirms ability-chain combat is planned ("real-time but deterministic, discrete ticks"). Path (b) is the intended destination; path (a) is the honest holding pattern until that sprint begins.

Item dictionary has no seam — its shape is an implicit contract

scenes/Shop.gd :_rebuild_inventory (reads item)

After — one factory function is the seam

Problem. The item dictionary {"element_id": …, "level": …} is assembled in two places (ShopSystem.buy_item and two functions in ForgeSystem) and read in two more. There is no seam — callers must know the key names, and any field addition touches all four files.

Solution. Add a make_item(element_id, level) factory to GameState.gd. Producers call it; consumers are unchanged. One place to add fields (e.g. ability_charges for the ability-chain sprint).

  • → locality: item shape concentrated at one seam
  • → leverage: adding a field later touches one line, not four
  • → small change, high payback as combat sprint begins

Top Recommendation

Candidate 1 — Phase State Machine

Phase transitions are the highest-traffic seam in the game loop — every scene touches them and every test must reason about them. Right now they are nowhere: scattered across three scene scripts as direct dictionary mutations. A PhaseSystem concentrates all valid transitions in one testable module, deletes the most confusing direct mutations in Battle.gd, and makes the state machine verifiable without scenes. It is also the logical prerequisite for everything in the combat sprint — new round logic, result handling, replay — so deepening it now pays forward immediately.

Pair with Candidate 4 (one-liner) as a warm-up before committing to Candidate 1.
