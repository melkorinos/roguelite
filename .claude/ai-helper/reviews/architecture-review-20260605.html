Strong in-process

After — one deep factory

flowchart TB
  COS[CombatSide
keys + slot count] --> CS
  CS["CombatState.begin(state, snapshot)
builds every per-slot array
+ stat rows from the board size"]:::deep
  CS --> GSx[GameState.create

one call, no literals]
  classDef deep fill:#10b981,stroke:#34d399,color:#04221a,stroke-width:2px;

Problem

What a valid combat-phase state is — its per-slot arrays and the 8× {"fires":0,…} stat-row literal — is hand-rolled in both GameState.create and to_battle, and the board size leaks as hardcoded 4-slot literals in 26 places.

Solution

A CombatState module owns "given a board, produce fresh combat state." It sizes every per-slot array from CombatSide's key list and the slot count; both callers delegate to it.

Wins

  • locality: combat shape lives in one module
  • leverage: grid-agnostic claim becomes real
  • deletes 16 duplicated stat-row literals
  • interface is the test surface: assert one factory
  • widening the grid is the one-place change the handoff wants
  • retires dead create_opponent_grid

02 · Extract the Element Card module

Strong in-process
scenes/slots/ShopItemTile.gd · scenes/slots/InventorySlot.gd
scenes/slots/BattleSlot.gd · scenes/screens/Shop.gd (_rebuild_inventory)

Before — three shallow renderers

ShopItemTile
emoji · name · price + hover timer
InventorySlot
"emoji\nname\nLvN dmg" + hover timer
BattleSlot
charge bar · emoji · "name LN" + hover timer

Three divergent layouts. None render the Tier badge, three stats, or Abilities Panel that ADR-0005 says the card always shows. The 0.3s hover-tooltip timer is copy-pasted verbatim in all three.

After — one deep card

ElementCard.render(elem, context)
icon · Tier badge · 3 stats · Abilities Panel · price
tier styling · hover-tooltip behavior
shop ctx inventory ctx battlegrid ctx

Each slot fills a slot-specific shell (drag, charge bar) around one shared card.

Problem

"Element Card" is a named domain module, but no module renders it — three slot scripts each re-implement a different subset, and none match ADR-0005's always-visible card.

Solution

One ElementCard node renders an element dict the same way everywhere; slots wrap it with their own affordances (drag, charge bar, buy click).

Wins

  • locality: one card layout, one place to change
  • code converges on ADR-0005 instead of drifting
  • deletes triplicated hover-tooltip timer
  • leverage: Abilities Panel appears in every context free
ADR-0005 describes the card but predates the slots — this aligns the code with the ADR, no conflict.

03 · Deepen the Shop action seam

Strong in-process
systems/ShopSystem.gd (transfer) · systems/ForgeSystem.gd
scenes/screens/Shop.gd (_on_buy_pressed, _on_*_received_drop)

Before — outcome leaks back to the scene

sequenceDiagram
  participant V as Shop.gd
  participant S as ShopSystem.transfer
  V->>V: gold_before = state.gold
  V->>S: transfer(...)
  S-->>V: new state (no outcome)
  Note over V: was it a buy or a reject?
  V->>V: diff gold to pick the sound
  Note over V: merge or swap?
scene inspects both elems,
picks level_up vs transfer

After — seam returns what happened

sequenceDiagram
  participant V as Shop.gd
  participant S as ShopSystem.drop
  V->>S: drop(from_loc, to_loc)
  S-->>V: { state, outcome }
  Note over V: outcome ∈ buy / merge /
swap / sell / rejected
  V->>V: play sound by outcome

Problem

The scene re-derives what an action did: it diffs gold to choose the buy/reject sound and counts inventory items to detect a merge, and it decides merge-vs-swap itself by inspecting both elements — domain rules living in a render script.

Solution

One intake drop(state, from, to) returns {state, outcome} — the same shape ForgeSystem.forge_from_bench already uses. The merge-vs-swap decision moves behind it.

Wins

  • pricing/merge rules stop leaking into the scene
  • matches ForgeSystem's existing outcome pattern
  • interface is the test surface: assert outcomes, not gold diffs
  • locality: "what does dropping A on B do" lives in one place

Worth exploring in-process

After — Action is an Ability effect list

flowchart TB
  FIRE[element fires] --> AA
  ABIL[ability triggers] --> AA["_apply_effects
(one effect vocabulary)"]:::deep
  AA --> SS[StatusSystem]
  Note["haste-timers + leech-from-damage
stay as named effect kinds"]
  classDef deep fill:#10b981,stroke:#34d399,color:#04221a,stroke-width:2px;
  class AA deep

Problem

An Action (on-fire T1 effect) and an Ability apply effects through two separate dispatchers. Most branches both bottom out in StatusSystem.apply_effect; only haste-timers and leech-from-damage are genuinely bespoke.

Solution

Model the on-fire Action as an effect list and route it through _apply_effects, with two new atomic kinds for the haste-timer and leech-from-damage cases.

Wins

  • locality: one effect vocabulary, one applier
  • matches the planned "Actions become Abilities" direction
  • leverage: new effects work for Actions and Abilities at once
  • interface is the test surface: one applier to cover
⚠ Touches ADR-0004, which split BattleSystem (call sites) from AbilitySystem (execution). Worth reopening only because the domain already plans Actions to fold into Abilities — confirm the depth-1 / RNG-ordering guarantees survive before committing.

05 · Make CombatSide the only side accessor

Worth exploring in-process

After — one accessor, both sides

flowchart TB
  CS["CombatSide
grid/statuses/timers/frozen(state, side)
+ opponent_of"]:::deep
  CS --> BSx[BattleSystem reads through it]
  CS --> ABx[AbilitySystem reads through it]
  classDef deep fill:#10b981,stroke:#34d399,color:#04221a,stroke-width:2px;
  class CS deep

Problem

CombatSide wants to be the single side→keys map, but BattleSystem shadows it with _make_side_ctx (renamed keys + opponent keys) and reads raw state[...] with manual casts; CombatSide's own accessors go unused there.

Solution

Move opponent-key and read helpers into CombatSide, delete the shadow ctx, and have both systems read side state through one accessor.

Wins

  • locality: side plumbing concentrates in one module
  • deletes the shallow re-wrapper ctx
  • fewer hand-rolled as casts at call sites
  • reinforces the "one-place change to grow the grid" goal

Top recommendation

Start with 01 — the combat-state factory

It is the highest-leverage, lowest-risk deepening: pure systems/data code already under test, no ADR conflict, and it removes the exact friction the abilities handoff flags — widening the Battlegrid today means editing four modules and 26 hardcoded literals. Concentrating combat-state shape in one factory makes the grid-agnostic claim real and unblocks the deferred Battlegrid-size decision. 02 (Element Card) is the strongest follow-up — most player-visible and the clearest locality win on the scene tier.
