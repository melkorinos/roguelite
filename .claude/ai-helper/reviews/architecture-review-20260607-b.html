1 · Unify Round resolution behind one outcome

systems/BattleSystem.gd · compute_result  |  systems/PhaseSystem.gd · describe_result, advance_round  |  scenes/screens/Battle.gd · _on_next_round_pressed

At the 30 s timeout with both sides alive, compute_result can show YOU WIN while advance_round scores it a loss and subtracts Life.

After — resolved once, read everywhere

flowchart TD
  E([combat ends]) --> RR["resolve_round(state)
→ RoundOutcome"]
  RR --> SHOW["render result"]
  RR --> RUN["advance the Run"]
  RR --> ACH["fire achievement"]
  classDef deep fill:#0f172a,stroke:#6366f1,stroke-width:2px,color:#e2e8f0;
  class RR deep

One win rule, one place to test it. Render, Run-advance, and achievements consume the same RoundOutcome.

Problem. Three call sites independently decide a Round's outcome, and two of them use different win rules — HP comparison vs opp_hp ≤ 0 — so the result shown and the result applied can disagree.

Solution. One module resolves a Round to a RoundOutcome (win/loss/draw, Life delta, wins-after, is_victory, is_eliminated, achievement event); describe_result, advance_round, and Battle.gd all read it instead of recomputing.

  • locality: one win rule, one place
  • kills the timeout shown-vs-applied divergence
  • interface is the test surface
  • leverage: render + advance + achievement share it
Decide the win rule on the way in. CONTEXT defines a Round win as opponent eliminated or margin in your favour — pick one and let the deepened module own it; this is the keystone for finalising the gameplay loop.

2 · Collapse the Shop intake into one verb

systems/ShopSystem.gd · transfer, resolve_drop, can_transfer, _buy, _buy_to_grid, _swap_arrays

_buy and _buy_to_grid differ only by the destination key — the buy-or-merge logic is copied.

After — one verb, destination as a parameter

resolve_drop(state, from, to) → {state, outcome}

internal — faded, parameterised by zone key

_place_or_merge(dest_key, …)
_swap_arrays · _first_empty

One buy-or-merge body; transfer stops being a second public entry.

Problem. Item movement has two public interfaces (transfer returns bare state, resolve_drop returns {state, outcome}), a can_transfer that re-walks the same case tree, and twin buy bodies that diverge only by destination array.

Solution. Make resolve_drop the single verb (mirroring the ForgeSystem attempt deepening already shipped); fold _buy/_buy_to_grid into one body keyed by destination, and make transfer/can_transfer private.

  • interface shrinks; implementation absorbs the twins
  • locality: buy-or-merge bug fixed once
  • deletion test: transfer just concentrates
  • same shape Forge already proved

After — create() delegates the combat shape

create()

CombatState.reset — the one owner of combat-phase shape

A new per-slot array is declared in exactly one place.

Problem. create() hand-rolls the same per-combat fields CombatState.reset() already owns; the two lists must be kept in sync by hand, and the ones create() sets are overwritten by reset() before combat ever reads them.

Solution. create() builds the Run-level fields, then calls CombatState.reset() for the combat shape — one owner for the per-slot arrays and Status pools.

  • locality: grid-shape change in one place
  • removes dead initial writes
  • deletion test: the duplicate list concentrates
  • smaller, intentional create()
