1. Contribution Bar computation belongs in BattleSystem

scenes/screens/Battle.gd · systems/BattleSystem.gd

Before

Battle.gd (scene)
_update_contrib_bars()
var _contrib_max: float = 1.0  ← game invariant
for each slot:
total = sum(contrib[type])
_contrib_max = max(_contrib_max, total)
w = (disp / _contrib_max) × BAR_WIDTH
rendering
seg.size = Vector2(w, BAR_HEIGHT)

Game invariant (_contrib_max is monotonic per combat) lives in a scene — untestable, mixed with pixel math.

After

BattleSystem
contribution_totals(state)
→ Array[float]
monotonic max logic here
pure, seeded, testable
Battle.gd
totals = BattleSystem
.contribution_totals(s)
seg.size = Vector2(
totals[i] × BAR_WIDTH, …)

Scene renders pre-computed values. Monotonic-max rule is testable in isolation.

Problem. Battle.gd carries _contrib_max — a per-combat running maximum that must be monotonically increasing and reset each combat. This is a game invariant, not a display constant. It sits next to pixel math in a scene, violating CLAUDE.md's "scene scripts handle rendering and input only" contract.

Solution. BattleSystem.contribution_totals(state) → Array[float] returns per-slot contribution sums from battle_stats. Battle.gd tracks the display max locally but gets the raw data from the seam — the monotonic invariant becomes testable via the system interface.

  • locality: monotonic-max rule concentrates in one testable place
  • leverage: one function, tested once, used by both live Battle and future Replay
  • scene shrinks — no game logic in the render loop
  • regression: can assert "total never decreases" in a unit test without a scene
Strong seam scatter

2. Drag payload has no module — three shapes, one decoder

scenes/slots/BattleSlot.gd · scenes/slots/InventorySlot.gd · scenes/slots/ShopItemTile.gd · scenes/screens/Shop.gd

Before

BattleSlot
{"type":"grid", "slot":N}
InventorySlot
{"type":"inventory", "slot":N}
ShopItemTile
{"type":"shop", "shop_slot":N}
BattleSlot._drop_data (line 80)
var from_slot: int =
  d["shop_slot"] if type=="shop"
  else d["slot"]
← key dispatch; silent -1 on typo

After

BattleSlot
DragLoc.grid(N)
InventorySlot
DragLoc.inventory(N)
ShopItemTile
DragLoc.shop(N)
DragLoc (data/)
static func grid(i) → {zone:"grid",slot:i}
static func inventory(i) → {zone:"inv",slot:i}
static func shop(i) → {zone:"shop",slot:i}
uniform shape; ShopSystem.can_drop already speaks {zone, slot}

Problem. The three slot types emit three distinct drag payload shapes. ShopItemTile uses "shop_slot"; the others use "slot". Every drop handler — BattleSlot._drop_data, InventorySlot._drop_data, SellZone._drop_data — must branch on type to pick the right key. A missing key falls silently to -1. No module owns the "drag location" type.

Solution. A thin DragLoc module (static class, data/) owns the three constructors and emits the {zone, slot} shape that ShopSystem.can_drop already speaks. All slot scenes call the factory; no slot scene decodes another slot's payload.

  • locality: drag-location type definition in one place
  • leverage: one shape; ShopSystem, BattleSlot, InventorySlot, SellZone all decode the same key
  • interface shrinks: drop handlers lose their branching key dispatch
  • tests: ShopSystem tests can build locations via DragLoc instead of raw dicts
Worth exploring seam crack

3. heal and leech bypass the EffectRegistry float-label seam

scenes/screens/Battle.gd:367–377 · data/EffectRegistry.gd

Before

Battle.gd · _spawn_float_labels()
if effect == "heal":
label("+1 HP", FLOAT_HEAL) ← hardcoded
elif effect == "leech":
label("+%d HP"%dmg, FLOAT_HEAL) ← hardcoded
else:
fx = EffectRegistry.float_label(effect)
label(fx["text"], …) ← seam
Two effects know about the amount-formating rule only in this scene. A third "HP-delta" effect requires knowing this exception exists.

After

Battle.gd · _spawn_float_labels()
fx = EffectRegistry.float_label_with_amount(
effect, dmg)
if fx: label(fx["text"], fx["color"], …)
EffectRegistry.gd (absorbs the rule)
static func float_label_with_amount(
effect: String, amount: int
) → Dictionary:
if effect == "heal": return …
if effect == "leech": return …
return float_label(effect)

Problem. EffectRegistry.float_label() is the declared single source for combat float labels — but heal and leech are hardcoded in Battle.gd:367–370. The seam exists and is used for all other effects, then quietly bypassed for two. Adding a future "HP-restoration" effect requires knowing this exception.

Solution. EffectRegistry.float_label_with_amount(effect, amount) absorbs the dynamic-amount formatting. Scene calls one function; EffectRegistry owns all float-label rules.

  • locality: all float-label rules in one module
  • interface shrinks: one call site in Battle.gd instead of three branches
  • future HP-delta effects automatically handled
Worth exploring interface width

4. ShopSystem: nine entry points over one concept

systems/ShopSystem.gd · test/unit/systems/test_shop_system.gd (668 lines)

Before — interface surface ≈ implementation

interface
transfer()
resolve_drop()
buy()
sell_item()
sell_grid_item()
grant_to_inv()
can_drop()
can_transfer()
reroll_shop()
+ 10 more…
implementation

Interface nearly as tall as implementation — shallow.

After — narrow interface, deep implementation

interface
transfer()
can_transfer()
reroll_shop()
implementation

buy / sell / grant expressed as transfer + price delta internally.

Problem. ShopSystem exposes ~20 public static functions. Most express the same concept — "move an element from one location to another, respecting rules" — behind separate entry points (buy, sell_item, sell_grid_item, grant_to_inventory, resolve_drop, transfer). Each caller must know which entry point fits its context. The test file is 668 lines — the largest system test — because the interface surface is so wide.

Solution. Narrow the public seam to transfer(state, from_loc, to_loc), can_transfer(state, from_loc, to_loc), and reroll_shop. Buy/sell/grant become internal transfer calls with a price delta. The Shop scene stops knowing which ShopSystem fn matches its context.

  • leverage: one transfer interface for all element moves
  • locality: "move rules" concentrate behind one seam
  • test surface shrinks; fewer scenarios to enumerate per call site
Note: transfer() already exists — the deepening is absorbing the specialised fns into it as internal paths, not adding a new seam. Low disruption.
Speculative duplicate declaration

5. ATOM_SCHEMAS is a second declaration of the atom vocabulary

systems/AbilitySystem.gd (ATOM_SCHEMAS) · data/AbilityData.gd (ABILITIES)

Before — two sources of truth

graph LR
  A["AbilityData.ABILITIES\n120 ability dicts\nwith effects:[{kind, ...}]"]
  B["AbilitySystem.ATOM_SCHEMAS\nrequired fields per kind\ndefault_target, potency_aware"]
  C["validate_atom(effect)"]
  A -->|"instances"| C
  B -->|"schema"| C
  classDef dupe stroke:#dc2626,stroke-width:2px
  class A,B dupe

A new atom kind requires changes in both files. A mismatch between the two is only caught when validate_atom runs.

After — one declaration

graph LR
  B["AbilitySystem.ATOM_SCHEMAS\nauthoritative atom vocabulary"]
  C["validate_atom(effect)"]
  D["AbilityData — atom instances\nreferenced by id"]
  B -->|"schema"| C
  D -->|"instances"| C
  B -.->|"new atom: add here only"| D
  classDef deep fill:#0f172a,stroke:#1e293b,color:#e2e8f0
  class B deep

ATOM_SCHEMAS is authoritative; AbilityData is the instance store. A new atom kind has one place to declare, one test to pass.

Problem. AbilitySystem.ATOM_SCHEMAS declares required fields and defaults for each atom kind. AbilityData.ABILITIES contains 120 ability dicts with atom instances. Adding a new atom kind requires both files. The test test_every_authored_effect_is_a_valid_atom is the only enforcement link — if it's not run, drift is silent.

Solution. Make ATOM_SCHEMAS the single authoritative atom vocabulary. AbilityData refers to it for field defaulting on read. The test becomes a structural guarantee rather than the only link.

  • locality: atom vocabulary in one const
  • leverage: validate_atom becomes redundant as atom construction enforces the schema
  • low risk: ATOM_SCHEMAS already exists; this is a documentation/discipline change as much as a code change
Speculative — the test suite already catches drift. Only worth doing if the atom vocabulary is expected to grow significantly (e.g., Trinket combat atoms, more Keystone atoms).

Top recommendation

#1 — Contribution Bar computation into BattleSystem

The monotonic-per-combat running max in Battle.gd directly violates the "scene scripts handle rendering and input only" contract in CLAUDE.md. It's the one candidate where the architectural rule is already written — the code just doesn't follow it. Fixing it gives you a testable, pure function for Contribution display data, and opens the door for the same logic to power the future Replay rendering path without scene access.

After that: #2 (drag payload scatter) is a one-afternoon fix that removes silent brittleness from the entire drag-and-drop surface.
