1. Consolidate lives-lost calculation in PhaseSystem

elif ratio >= 0.30: return 20

Problem. The lives-lost threshold calculation (ratio ≥ 0.70 → 30, ≥ 0.30 → 20, else 10) is copy-pasted identically into advance_round and describe_result. Both must be kept in sync by hand. A balance change to one threshold — e.g. tightening "hard loss" from 70% to 65% — requires editing two functions. If the edit lands in advance_round but not describe_result, the result preview screen shows a different lives-after than the one that actually gets applied: a visible player-facing inconsistency.

Solution. Extract static func _lives_lost(ratio: float) -> int in PhaseSystem. Both advance_round and describe_result call it. One test covers the thresholds once. Balance changes are a one-line edit with guaranteed consistency.

  • ✦ Locality: all Lives loss logic in one function — the balance designer's single edit point
  • ✦ Leverage: both callers get the same formula with no coordination cost
  • ✦ Deletion test: delete one copy of the formula — the other caller now uses stale thresholds. That's the cost being paid right now.

Latent bug in the current code — "slow" is missing from _status_count

StatusSystem.empty_statuses() defines "slow": {"n": 0}. But AbilitySystem._status_count() has no case for "slow" — it falls through and returns 0. Any ability condition {"kind": "target_has_status", "status": "slow", "at_least": 1} will always evaluate false, regardless of actual slow stacks. Adding a T2/T3 ability that reacts to slow would silently never trigger. This is the direct consequence of the metadata living in two places with no enforcement.

Problem. A new element effect (any future T2/T3 design) must update four locations across three files: its status shape in StatusSystem.empty_statuses(), its on-fire mechanical behaviour in BattleSystem._apply_element_effect(), its reactive trigger string in AbilitySystem._event_triggers(), and its condition-readable count field in AbilitySystem._status_count(). These four pieces of knowledge describe one concept — what an effect is — but they live in three separate modules with no shared structure. The missing "slow" case in _status_count is the current cost: slow-condition abilities silently always evaluate false.

Solution. Introduce an EffectRegistry in data/ — a Dictionary keyed by effect name, each entry holding status_shape, trigger, and count_field. StatusSystem.empty_statuses(), AbilitySystem._event_triggers(), and AbilitySystem._status_count() become thin readers of this table. BattleSystem._apply_element_effect() keeps its match for the handful of effects with non-trivial on-fire mechanics (haste, heal, cleanse, leech); all others auto-route through StatusSystem.apply_effect() as they do today.

  • ✦ Locality: adding "frost" is one table entry; the three readers derive everything from it
  • ✦ Leverage: the registry also powers the Compendium, Tooltip Abilities Panel, and any future effect documentation — same data, no duplication
  • ✦ Deletion test: delete _status_count. Complexity reappears as "what field holds the count?" spread across every caller that tries to condition on a status. The registry concentrates that answer in one place.
  • ✦ Fixes the current bug: "slow" gets a row; the latent silent failure disappears at the source.

Top recommendation

Start with #2 — EffectRegistry

T2/T3 effect design is the next major work item. Every effect added before this is fixed pays the four-location tax and risks a silent bug like the current "slow" case. Candidate #1 (lives-lost) is a one-function extraction — low risk, any session. Candidate #2 has compounding cost: each new effect makes the split harder to close. Do it before the T2/T3 roster grows.
