Problem

AbilitySystem is five concerns in 603 lines — ability lookup, effect application, reactive grid scanning, event factories, and atom validation — with no internal seams. A reactive-firing bug and an effect-vocabulary bug both live in the same module. Every caller's test crosses the same wide interface.

Solution

Extract ReactiveResolver: takes the event list + state, returns updated state + new events. The grid-scan loop, trigger-matching, depth-1 enforcement, and effect dispatch all move behind this one seam. AbilitySystem shrinks to a pure atom-vocabulary registry and ability lookup — a shallow module that earns its shallowness.

Wins

  • · locality: reactive bugs concentrate in one module
  • · leverage: one resolve() interface covers all Ability triggers
  • · AbilitySystem interface shrinks to lookup + validation
  • · test surface maps one-to-one with each concern
  • · Innate Ability + Replay slot naturally into ReactiveResolver

Problem

describe() — a 30-line presentation match block — lives inside the same module as tick() and compute_incoming_damage(). A Status Readout text change requires touching core game logic. A game-logic bug can be masked by a display test passing.

Solution

Extract StatusReadout: takes a status name and the live statuses dict, returns display strings. StatusSystem stays pure game logic. StatusChip and any future Status Tray or battle HUD element calls StatusReadout exclusively — no path from display callers into game logic.

Wins

  • · locality: display bugs and game bugs in separate modules
  • · leverage: StatusReadout is the single display seam for all 12 Status effects
  • · StatusSystem shrinks to 9 functions — all game logic
  • · StatusReadout is independently testable against any statuses dict

4 · Fix the resolve_reactive_inplace mutation contract

Worth exploring

systems/AbilitySystem.gd  ·  systems/BattleSystem.gd

Before — invisible ordering constraint

sequenceDiagram
  participant BS as BattleSystem
  participant AS as AbilitySystem
  Note over BS: caller must .duplicate() first
  BS->>BS: copy = state.duplicate(true)
  BS->>AS: resolve_reactive_inplace(copy, events)
  Note over AS: mutates copy in-place
  AS-->>BS: void
  BS->>BS: state = copy
  Note over BS: forget the duplicate →
silent state corruption

After — contract at the seam

sequenceDiagram
  participant BS as BattleSystem
  participant RR as ReactiveResolver
  Note over BS: no duplication needed
  BS->>RR: resolve(state, events)
  Note over RR: duplicates internally
  RR-->>BS: new_state (fresh dict)
  BS->>BS: state = new_state
  Note over BS: same convention as
every other system

Problem

resolve_reactive_inplace() mutates the passed dict in-place. Every other module in systems/ returns a new dict — the codebase convention is explicit. This function's ordering constraint (caller must .duplicate() first) is invisible in the interface. A future caller who skips the duplicate silently corrupts state with no error.

Solution

Rename to resolve_reactive(state, events) → Dictionary and move the duplicate inside. The ordering constraint disappears from the interface and lives at the seam. This is a low-churn change: one rename, one .duplicate() moved, one void return changed.

Wins

  • · interface: ordering constraint lives at the seam, not in caller docs
  • · locality: mutation behavior concentrates inside the module
  • · future callers cannot accidentally corrupt state
  • · codebase convention is uniform across all 13 system modules

Adding a 6th flag = change configure() only. Ordering constraint is invisible to all 4 subclasses.

⚠ Godot scene inheritance may resist a static factory — verify engine lifecycle before committing

Problem

Five flags must be set before super._ready() — a Godot lifecycle ordering constraint invisible in the type signature. Each of the 4 Element Card subclasses repeats the pattern. Adding a new flag touches all four. Missing the ordering silently breaks layout.

Solution

A named factory ElementCard.configure(opts) that bundles flag-setting + add_child in the correct order internally. Subclasses call the factory; the ordering constraint disappears from their interface.

Wins

  • · interface: ordering constraint explicit at the seam
  • · locality: new flag = change configure() only
  • · leverage: 4 subclasses share one creation path
  • · engine compatibility uncertain — speculative

Top recommendation

Candidate 1 — Extract the Reactive Resolver

AbilitySystem is the largest module at 603 lines and the seam through which every Combat Event passes during a fight. Extracting ReactiveResolver gives the deepest single-module deepening available: the reactive-firing loop — grid scan, trigger-match, depth-1 enforcement, effect dispatch — hides behind one function. AbilitySystem becomes a pure vocabulary registry. Every future Ability addition, reactive bug, Innate Ability hook, and combat-trigger test hits a smaller, more focused interface. Candidate 4 (mutation contract fix) is a natural companion and can land first — it's a one-line rename that aligns the interface with the convention the rest of systems/ already follows.
