Problem. AchievementSystem.check() reads and writes PlayerProfile on every call — disk I/O inside a function billed as a pure system transform. Callers in Battle.gd and Shop.gd discard the return value entirely and rely on side effects. The seam between achievement logic and persistence doesn't exist.

Solution. Extract persistence behind a ProfileAdapter seam; check() takes a profile snapshot dict and returns {unlocked: []} — no I/O. Callers apply the unlocked list and persist via the adapter. evaluate() (already pure) becomes the only real implementation.

  • ✦ Locality: all achievement logic concentrates in one module, testable without disk
  • ✦ Leverage: one interface covers both Battle and Shop call sites
  • ✦ Two adapters justify the seam: ConfigFileAdapter in prod, DictAdapter in tests

2. Collapse the tick_battle firing loop

Strong in-process

systems/BattleSystem.gd

Before — shallow, duplicated

tick_battle(state, delta) — 109 lines
status tick + HP damage (opponent)
player firing loop (lines 60–94)
opponent firing loop (lines 97–133) ← near-identical
FeatureFlags.status_effects branch ×6
_apply_element_effect(…, is_player_side, timers)
player & opponent loops differ only in key names

After — deep, single loop

tick_battle(state, delta)
for side in [player_ctx, opponent_ctx]:
_tick_side(side_ctx, opp_ctx, s)
— handles tick, fire, effect, status
BattleSideContext { grid, timers, statuses, hp_key }
flag branches hidden inside _tick_side; callers don't see them

Problem. tick_battle() runs the player firing loop (lines 60–94) and the opponent firing loop (lines 97–133) as near-identical duplicates, separated only by is_player_side boolean and dictionary key names. FeatureFlags.status_effects branches appear six times across both copies. The function is 109 lines with no test coverage — the most consequential code in the game is untestable at the Ability Chain level.

Solution. Introduce a BattleSideContext value (plain Dict: grid, timers, statuses, hp_key) and collapse to a single _tick_side(own_ctx, opp_ctx, s) helper. tick_battle constructs two contexts and calls it twice. Feature flag branches live once, inside _tick_side.

  • ✦ Locality: firing logic has one place to change; adding Burn stacking changes one code path, not two
  • ✦ Leverage: _tick_side is unit-testable against any two-context pairing (player vs ghost, ghost vs ghost)
  • ✦ Interface shrinks: _apply_element_effect's is_player_side flag disappears into the context dict

Problem. ForgeSystem exposes 10 functions with three different return contracts: plain new-state Dict (level_up, forge, move_to_forge_slot…), outcome-code Dict (forge_from_bench), and String (preview). Callers in Shop.gd must know which function returns what — the module's interface is nearly as complex as its implementation. Recipe discovery is detected by scene-level before/after count comparison, not by the Forge module itself.

Solution. Collapse the write side to attempt(state, op: Dictionary) → {state, ok: bool, outcome: String, new_recipe: bool}. Operations are {type: "level_up"|"forge"|"bench_place"|...}. All bench and slot operations route through one function; scenes stop doing before/after counting.

  • ✦ Locality: recipe discovery moves from scene into Forge module where it belongs
  • ✦ Leverage: one interface, one test fixture for all Forge operations
  • ✦ Interface shrinks from 10 function signatures to 2

Problem. Three slot components (BattleSlot, InventorySlot, ForgeSlot) each call ShopSystem.can_transfer(GameManager.state, from_loc, to_loc) directly from their _can_drop_data() methods. The {"zone": ..., "slot": ...} location dictionary shape is a detail of ShopSystem's implementation that has leaked across the seam into three separate UI modules.

Solution. Add GameManager.can_drop(from_zone, from_slot, to_zone, to_slot) → bool. Slots call that. Transfer-rule changes go in one module; slots never see location dict shape.

  • ✦ Locality: transfer validation lives in one module; change the rule once
  • ✦ Leverage: all three slots (and future slots) share one call
  • ✦ Deletion test: delete ShopSystem.can_transfer — complexity would reappear in three slot files. That's the signal.

5. Consolidate battle-init constants into GameState

Speculative in-process

data/GameState.gd  ·  systems/PhaseSystem.gd

Before — magic 30 appears three times

GameState.create()

"player_hp": 30  ← magic

PhaseSystem.to_battle()

s["player_hp"] = 30  ← again

s["element_timers"] = [0,0,0,0]  ← hardcoded

PhaseSystem.advance_round()

s["player_hp"] = 30  ← third copy

s["gold"] += 5  ← magic

After — one source of truth

GameState (constants)

PLAYER_HP_MAX = 30

GOLD_PER_ROUND = 5

GRID_SIZE = 4

PhaseSystem.to_battle()

s["player_hp"] = GameState.PLAYER_HP_MAX

PhaseSystem.advance_round()

s["gold"] += GameState.GOLD_PER_ROUND

Problem. player_hp = 30 is hardcoded in GameState.create(), PhaseSystem.to_battle(), and PhaseSystem.advance_round(). Same for gold += 5 and [0.0, 0.0, 0.0, 0.0] timer init. When these constants need tuning — which they will during balance work — three files must change and tests must catch any miss.

Solution. Promote to named constants in GameState.gd (PLAYER_HP_MAX, GOLD_PER_ROUND, GRID_SIZE). All systems reference the constant; the magic number lives in exactly one place. Low-risk change; high locality payoff during balance iteration.

  • ✦ Locality: tuning HP cap or round gold is a one-line change
  • ✦ Leverage: constants reachable from all systems without duplication

Top recommendation

Start with #2 — Collapse the tick_battle firing loop

BattleSystem.tick_battle() is the heart of the Ability Chain — the single most consequential function in the game — and it has zero test coverage. The duplicated player/opponent loops mean every new Effect (Burn stacking, Weaken, future T2 mechanics) requires two parallel edits with no guard against divergence. Fixing this now, before the Ability Chain design is settled, costs less than fixing it after six more Status Effects are added. Candidates #1 and #5 are complementary but less urgent.
