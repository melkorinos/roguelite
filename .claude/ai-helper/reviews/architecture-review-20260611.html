1 · Finish EffectRegistry as the single per-effect source

Strong in-process

  FL["Battle._spawn_float_labels\nOWN emoji+text+color map\n(213–225)"]

After — one table, both readers

flowchart TB

  ER2 --> ST2

Problem.
EffectRegistry's own docstring calls it "single source of truth for per-effect metadata," yet Battle._spawn_float_labels hardcodes a second effect→emoji/text/color map. They already disagree: blind 🙈 vs 👁, poison 🧪 vs ☠, plating 🧱 vs ⚙ — the same Status shows different icons in the tray and the float label.
Solution.
Add float_text + color (the one thing the registry lacks) to each EFFECTS entry. _spawn_float_labels looks the effect up instead of matching on it. The leech/heal dynamic "+N HP" text stays computed at the call site.
Wins.
  • locality: one row per effect, drift can't recur
  • leverage: tray + float labels + future Compendium read one table
  • deletes the 12-branch match in a render-only scene

2 · Stop reading Status internals across the seam

Worth exploring in-process

systems/StatusSystem.gd (owns the shape) · systems/BattleSystem.gd:168 · systems/AbilitySystem.gd

flowchart LR
  ER[("EffectRegistry.status_shape\nblind:{percent} armor:{value}\nshock:{n} curse:{stacks}…")]
  SS["StatusSystem\n(owns shape)"]
  BS["BattleSystem\n((s[k])['blind'])['percent']"]
  AS["AbilitySystem\n(statuses[name])['field']"]
  ER --> SS
  BS -.knows shape.-> ER
  AS -.knows shape.-> ER
  classDef leak stroke:#dc2626,stroke-width:2px;
  class BS,AS leak
Problem.
The status-dict shape (which field each Status stores) is declared in EffectRegistry.status_shape and applied by StatusSystem — but BattleSystem and AbilitySystem reach straight through it with nested casts like ((s[key]["blind"]))["percent"] as int. Every caller that reads a Status must memorise its internal field names; rename a field and the casts break silently.
Solution.
StatusSystem exposes typed readers — a generic field(statuses, name, key, default) plus a few named ones (blind_percent, armor_value) where the call site reads best. Callers ask StatusSystem; the shape stops leaking.
Wins.
  • locality: the status shape lives behind one interface
  • the nested triple-cast disappears from the hot path
  • deletion test: removing the readers re-spreads the casts → concentrates
Related to #5 — this is the narrow accessor; #5 is the larger "make StatusSystem generic" play. Do this one first; it stands alone.

3 · Move the Round-result text into PhaseSystem

Worth exploring in-process

scenes/screens/Battle.gd:278–304 · systems/PhaseSystem.gd

Before — scene interprets the win rule

PhaseSystem.resolve_round → {outcome, is_victory, is_eliminated, wins_after, lives_after}
Battle.gd match outcome:
+ branch on is_victory / is_eliminated
→ "🏆 VICTORY" / "✅ YOU WIN" / "💀 ELIMINATED" …
+ next-button label

After — scene just renders strings

PhaseSystem.result_text(state)
→ { text, next_label }
Battle.gd: label.text = rt.text
Problem.
Battle.gd takes describe_result and branches on is_victory/is_eliminated to compose the win/loss/draw text and the next-button label — 25 lines of win-rule interpretation in a render-only scene. The "you understand exactly why" result copy (soul.md) has no test.
Solution.
PhaseSystem.result_text(state) → { text, next_label }, next to resolve_round which already owns the outcome. Battle.gd renders the strings.
Wins.
  • the win-rule vocabulary lives entirely in PhaseSystem
  • result copy becomes unit-testable
  • restores the rendering boundary in Battle.gd
Single caller today, so the leverage is modest — the case is the rendering rule + testability, not N call sites. Same shape as pass-#5's presenter.

4 · Name the combat triggers and effect kinds once

Speculative constants

data/AbilityData.gd · data/EffectRegistry.gd · systems/AbilitySystem.gd · systems/BattleSystem.gd:211 · systems/StatusSystem.gd:237

flowchart LR
  E1['on_armor_stripped']
  AD["AbilityData\n(TRIGGER_LABELS + ability defs)"]
  ER["EffectRegistry.triggers"]
  BS["BattleSystem emits\n:211"]
  SS["StatusSystem emits\n:237"]
  AS["AbilitySystem matches\n+ inline concat"]
  E1 --- AD
  E1 --- ER
  E1 --- BS
  E1 --- SS
  E1 --- AS
Problem.
Trigger names (on_armor_stripped, on_poison_tick, on_haste_applied…) and effect-kind strings (apply_status, deal_damage, freeze…) are bare literals in 3–5 files each. An emitter typo silently matches no reactive — a whole synergy just fails, no error. Compound triggers are built by inline string concat ("on_status_applied:" + status).
Solution.
A CombatNames (or Triggers + EffectKinds) constants holder; emitters and matchers reference the constant, and one helper builds compound trigger names.
Why only Speculative.
  • honest: a name registry, not a deep module — no behaviour hides behind it
  • value is typo-safety + discoverability, not leverage
  • worth pairing with a test that asserts every emitted trigger is declared

5 · One Status descriptor; StatusSystem goes generic

Speculative in-process

data/EffectRegistry.gd · systems/StatusSystem.gd (is_active / apply_effect / describe / chip_badge)

Before — a new Status touches 3 files

EffectRegistry
shape/emoji

StatusSystem
is_active·apply
·describe·badge
(per-status if/else)

AbilityData
defs

After — the descriptor carries the rules

EffectRegistry entry
shape·emoji·badge
·active_when·describe

StatusSystem
generic engine

Problem.
"What a Status is" is split: EffectRegistry holds shape + emoji + count_field, while StatusSystem hardcodes per-status logic in is_active, apply_effect, describe, and chip_badge. Adding a Status means editing all of them in sync.
Solution.
Push the per-status rules — the "active when" predicate, the badge field, the describe template — into each EFFECTS entry, so StatusSystem becomes a generic applier/describer driven by the descriptor.
Why only Speculative.
  • per-status logic is genuinely varied (curse charges, weaken ticks) — some won't datafy cleanly
  • large surface; best tackled deliberately, after #1/#2
  • but the locality payoff is real: one row defines a Status end to end

Also noted — smaller, low-risk

  • Undo encapsulation leak. Shop._apply_drop sets GameManager.undo_state = before.duplicate(true) inline (Shop.gd:329) while every other site uses GameManager.save_undo(). Give GameManager a guarded save_undo() the scene can call unconditionally, or a capture_for(outcome) — one place owns undo capture.
  • Ghost snapshot factory. The {player_id, player_name, round, grid, acquired_day, source} shape is hand-built in OpponentProvider and three times in GhostFixtures. A Ghost.snapshot(...) factory gives the shape one home (the grid-building stays per-source). Low volatility, so low priority.
  • DPS math in Battle.gd:383. float(dmg) / battle_time is a derived stat in the render path — a one-line BattleSystem.dps(...) would keep combat math out of the scene. Tiny.

Top recommendation

Start with #1 — finish EffectRegistry.

It fixes a live bug — three Statuses already show different emoji in the tray vs the float label — and it just completes a job EffectRegistry already claims to own, so the risk is minimal. It's the same "one source for display vocabulary" theme that worked in pass #5. Then #2 (Status field readers) stops the shape leaking across the combat seam and sets up the bigger #5 if you later want StatusSystem fully generic. #3 and the undo cleanup are quick wins whenever convenient.

Sequence: 1 → 2 → 3 → (5 when you want the big consolidation) · #4 only with a guard test.
