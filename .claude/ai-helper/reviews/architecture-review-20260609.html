Problem. "Build a live Element from its definition" (duplicate the shared const dict, set element_id + level) is reimplemented in 7 places — the recent Event + Ghost work added two more.

Solution. One ElementData.instantiate(id, level) that returns a fresh, owned instance dict. Callers set their extras (Starting Pick's damage_multiplier, a forge's result id) after.

  • locality: instance shape defined once
  • leverage: one interface, 7 call sites
  • guards the zero-copy find() contract (always duplicates)

B · One notion of board power (route HP through effective_damage)

Worth exploring in-process

systems/BattleSystem.gd:29 (compute_opponent_hp) · data/ElementData.gd:177 (effective_damage) · systems/AchievementSystem.gd:74

before — two seams disagree on "how strong is this element"

flowchart LR
  E["Element instance\n(damage, level, tier)"]
  ED["ElementData.effective_damage\n= damage×level + tier\n(LEVEL-AWARE)"]
  CH["compute_opponent_hp\n= Σ raw damage × 5\n(LEVEL-IGNORANT)"]:::leak
  E --> ED
  E --> CH
  ED -. "actual hits scale with level" .-> OUT1["opponent offence ↑"]
  CH -. "HP ignores level" .-> OUT2["opponent HP plateaus ~230"]:::leak
  classDef leak stroke:#dc2626,stroke-width:2px;

after — HP keys off the same canonical value

flowchart LR
  E["Element instance"]
  ED["ElementData.effective_damage\n(single source of element worth)"]:::deep
  CH["compute_opponent_hp\n= Σ effective_damage × k"]
  E --> ED --> CH
  CH --> OUT["opponent HP rises with tier AND level\n→ late curve can sit at ~50%"]
  classDef deep fill:#0f172a,color:#e2e8f0,stroke:#0f172a;

Problem. The new round-scaled Ghosts gain Level, so their offence scales — but compute_opponent_hp sums raw damage and ignores level, so opponent HP plateaus at ~230 from round 7. Two definitions of "element worth" that drift.

Solution. Sum effective_damage(elem) instead of raw damage in compute_opponent_hp (and the same in AchievementSystem). "What an element is worth" lives in one place.

  • locality: element worth defined once
  • fixes the opponent-HP plateau (G4)
  • leverage: tier + level both feed HP
⚠ Shifts opponent HP values — it's a balance change as much as a deepening. Do it inside the paused G4 pass, then re-sweep, not as a silent refactor.

C · A "grant Element to inventory" operation

Worth exploring in-process

systems/StartSystem.gd:38 (apply_starting_pick) · systems/EventSystem.gd:_grant_element · systems/ShopSystem.gd (_first_empty_slot)

before — two near-identical grant routines

find empty inv slot → instantiate → place · else gold fallback

grant_element(state, id, level, on_full)

StartSystem
EventSystem

Problem. "Drop a granted Element into the first empty inventory slot" is implemented twice (Starting Pick, Event reward), each with its own full-inventory handling.

Solution. One grant_element seam (built on factory A), with the full-inventory policy as a parameter (gold-equivalent for Events, no-op for Starting Pick).

  • locality: grant rules in one module
  • composes with factory A
  • interface is the test surface

D · Run Modifier registry

Speculative in-process

data/GameState.gd · systems/EventSystem.gd · systems/PhaseSystem.gd (_scaled_player_hp) · systems/ShopSystem.gd (reroll_cost)

knowledge of "what Run Modifiers exist" is spread across 4 modules

flowchart TD
  R["EventSystem.apply_reward"] -->|writes| HB["hp_bonus field"]
  R -->|writes| RD["reroll_discount field"]
  HB -->|read in| PS["PhaseSystem._scaled_player_hp"]:::leak
  RD -->|read in| SS["ShopSystem.reroll_cost"]:::leak
  GS["GameState.create\n(declare + init each)"] -.-> HB & RD
  AR["advance_round\n(reset some, not others)"] -.-> RD
  classDef leak stroke:#dc2626,stroke-width:2px;

Problem. Each new persistent reward = a new field + a new read site + a remember-to-(not)-reset decision, with no module that knows the modifier set. Shallow spread that grows with every reward.

Solution. A small registry: each Run Modifier declares its key, default, and reset cadence in one place; consumers ask the registry. Deepens as the reward pool grows.

⚠ Contradicts ADR 0011, which deliberately chose discrete fields over a generic modifier list ("over-engineering for two modifiers"). Only reopen once the modifier count is clearly past a handful — at two the discrete fields win. Listed for honesty, not action.

Top recommendation

A · Element instance factory

Highest leverage, zero behaviour change, and squarely on the recent work — the Event and Ghost features each added a fresh copy of the instantiation pattern. One ElementData.instantiate concentrates the instance shape, protects the zero-copy find() contract, and gives A→C a base to build on. Then fold B into the G4 balance pass (it fixes the HP plateau but moves numbers, so it belongs with a re-sweep, not a silent refactor).
