data/ElementData.gd · find / all_elements  |  data/RecipeData.gd · all_recipes / find_result / recipes_with / recipes_for / ingredients_of

AbilityData.get_ability is already ABILITIES.get(id,{}) over a const dict — O(1), built once. Element/Recipe never got the same treatment.

After — const data + lazy indices behind the same interface

flowchart TD
  R[callers unchanged] --> I["find / recipes_for / recipes_with"]
  I --> IDX["lazy static index
id→elem · ingredient→recipes · result→recipes"]

Interface identical; implementation absorbs the cache. The roster just stabilised (dead-ends fixed), so the long-standing PERF deferral is now safe to cash in.

Problem. Two of the three data modules rebuild their full array and scan linearly on every lookup, inside render loops — while the third (AbilityData) already proves the indexed shape.

Solution. Make ELEMENTS/RECIPES const (or lazy-cached) and add id/ingredient/result indices, behind the unchanged find / recipes_* interface.

  • leverage: every render + lookup path
  • locality: caching in one module
  • interface unchanged → tests untouched
  • copy AbilityData's proven shape

2 · One drag-drop intake seam

scenes/slots/{InventorySlot,BattleSlot,ForgeSlot,SellZone,ShopItemTile}.gd · _can_drop_data / _get_drag_data  |  systems/ShopSystem.gd · transfer / can_transfer / resolve_drop

  S2[BattleSlot] -->|build from/to loc| CT

Apply goes through resolve_drop; validation goes through can_transfer; transfer is a third near-passthrough. Each slot re-derives the loc descriptor.

After — one drag descriptor, two verbs over it

flowchart TD
  SLOTS[all 5 slots] -->|drag descriptor| DI["can_drop(state, drag)"]
  SH2[Shop.gd] --> DI2["resolve_drop(state, drag)"]
  DI --> IMPL["intake impl

  DI2 --> IMPL
  classDef deep fill:#0f172a,stroke:#6366f1,stroke-width:2px,color:#e2e8f0;
  class DI,DI2,IMPL deep

Validation crosses the same seam as apply. Drop rules live in one place; the slots stop knowing zone/slot vocabulary.

Problem. Drop validity is decided slot-by-slot (each builds its own loc dicts and picks a verb), and the intake module exposes three overlapping public verbs.

Solution. One drag descriptor + a can_drop/resolve_drop pair both slots and Shop speak; fold transfer/can_transfer into the implementation.

  • locality: drop rules in one module
  • validation = apply's test surface
  • interface shrinks 3 verbs → 2
  • slots stop re-deriving zone/slot
Note: ~40 tests pin transfer/can_transfer as public — make them private only with a test migration to the new seam, or keep them as thin internal-but-tested shims.

5 · create() delegates the combat shape to reset()

data/GameState.gd · create()  ↔  data/CombatState.gd · reset()

Problem. create() hand-rolls the per-combat fields (timers, frozen, ability-timers, statuses, battle_stats) that CombatState.reset() already owns — two field lists kept in sync by hand, and create()'s copies are overwritten before combat reads them.

Solution. create() builds the run-level fields, then calls CombatState.reset() for the combat shape — one owner for the per-slot arrays.

locality: grid-shape change in one place · removes dead initial writes · (open from the 2026-06-04 review).

7 · Stop tearing down the whole Shop on every render

Shop.gd · _rebuild_shop_grid / _rebuild_inventory / _rebuild_battle_grid / _rebuild_forge_bench

Problem. Every _render() queue_free()s and recreates all shop/inventory/grid/forge nodes (and re-wires every signal) — a full UI teardown on each interaction. Cheap today (~20 nodes), but it compounds with candidate 1's per-node data scans, and grid growth multiplies it.

Solution. Persistent slot nodes updated in place (set element / clear), rebuilt only on count change. Bigger rework; flagged so it's on the radar, not urgent.

Speculative: real but low-pain now; revisit alongside candidate 1 or grid growth.
