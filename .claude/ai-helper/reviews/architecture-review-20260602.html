1. Deepen PhaseSystem: pull result logic out of Battle.gd

Strong locality

After

PhaseSystem owns every result transition; Battle.gd reads state and renders

Problem. Battle.gd contains three pieces of domain logic: the 10-win victory check (line 139), the HP-ratio → lives-lost formula (lines 151–156), and a direct state mutation GameManager.state["phase"] = "shop" (line 301). The same ratio formula already exists in PhaseSystem.advance_round() (lines 42–47) — a triple redundancy with BattleSystem.compute_result().

Solution. PhaseSystem.advance_round() returns the complete next state including result, lives, and phase; Battle.gd calls it once and passes the state to _render().

  • ✦ locality: win/loss rules in one module, zero duplication
  • ✦ interface shrinks: Battle.gd calls one function, reads one state key
  • ✦ scene boundary restored: no direct state mutations in Battle.gd
  • ✦ test surface: phase transitions testable entirely through PhaseSystem

Problem. Four slot nodes each contain their own _can_drop_data() implementation. BattleSlot reads GameManager.state["gold"] and state["battle_grid"] directly — scene nodes reaching into the state layer, violating the rendering boundary. A change to transfer rules requires editing N slot classes.

Solution. Add ShopSystem.can_transfer(state, from_loc, to_loc) → bool alongside the existing transfer(). Each slot node delegates to it; nodes stop reading state directly.

  • ✦ locality: transfer rules in one module — change once, applies everywhere
  • ✦ scene boundary restored: slot nodes never read GameManager.state
  • ✦ leverage: can_transfer testable without any scene nodes
  • ✦ delete 4 shallow validation implementations

4. Deepen AchievementSystem: absorb the caller orchestration

Worth exploring interface · leverage
systems/AchievementSystem.gd
scenes/screens/Battle.gd :325, :337–346 (_apply_and_save_profile)
scenes/screens/Shop.gd :349, :349–358 (_fire_achievement)
autoloads/PlayerProfile.gd

Before — scene must orchestrate 3 calls

sequenceDiagram
    participant S as Battle.gd / Shop.gd
    participant A as AchievementSystem
    participant P as PlayerProfile
    S->>A: check(state, profile.to_dict(), event)
    A-->>S: updated profile dict
    S->>P: from_dict(updated)
    S->>P: save_profile() [immediate or batch]
    note over S: caller decides save timing

After — one call, all decisions inside

sequenceDiagram
    participant S as Battle.gd / Shop.gd
    participant A as AchievementSystem
    participant P as PlayerProfile
    S->>A: check(state, event)
    A->>P: reads + writes profile internally
    A-->>S: updated state + unlocked[] list
    note over S: scene only reads unlocked[] to show UI

Problem. Every AchievementSystem caller (Battle.gd and Shop.gd) must: call AchievementSystem.check(), unpack the result dict, call PlayerProfile.from_dict(), then decide whether to call save_profile() immediately or batch. Save-timing logic is duplicated — and inconsistently implemented between the two callers.

Solution. AchievementSystem.check(state, event) → {state, unlocked} reads and writes PlayerProfile internally. Callers receive only the minimal result they need for UI feedback (list of newly unlocked IDs).

  • ✦ leverage: save-timing logic moves from N callers to one module
  • ✦ interface shrinks from 3 parameters to 2; return type from fat dict to focused pair
  • ✦ locality: achievement + profile state stays inside the system seam
  • ✦ note: requires AchievementSystem to accept PlayerProfile as a collaborator (injected or autoload reference)
Trade-off: Pure-static systems currently take no autoload references. This deepening adds PlayerProfile as an implicit dependency — consider whether that's acceptable before proceeding.

Problem. forge_from_bench() returns a dict with mixed concerns: the new game state, a UI-facing outcome string, and a level_mismatch boolean flag. This breaks the clean state → new state pattern every other system follows. Callers must destructure three keys; adding a new outcome means touching all callers.

Solution. Return {state, outcome_code} where outcome_code is an int constant (FORGE_OK, FORGE_LEVEL_MISMATCH, FORGE_NO_RECIPE, etc.). Shop.gd maps codes to UI strings — presentation stays in the scene layer.

  • ✦ interface narrows to match every other system's state-in/state-out contract
  • ✦ locality: outcome semantics live in one constants block
  • ✦ new outcomes don't change the return shape — callers add a match branch, not a new dict key

Problem. GodotSteam requires a custom engine build and is incompatible with web export. Currently there is no seam between AchievementSystem and the Steam SDK — when Steam calls are added, they will land directly in scene or system code and break the web build path.

Solution. A PlatformLayer autoload with a SteamAdapter (desktop) and NoOpAdapter (web/dev) behind one interface. AchievementSystem calls PlatformLayer.unlock_achievement(id) — never the SDK directly. This is the only seam in the codebase with a committed second adapter, making it a real seam worth building now.

  • ✦ two adapters exist (Steam + NoOp) → real seam, not hypothetical
  • ✦ web and desktop export can share the same source tree
  • ✦ NoOpAdapter serves as the test adapter — no Steam SDK required in CI
  • ✦ locality: all SDK version concerns behind one module
Note: This candidate is architectural scaffolding — the seam is load-bearing before any Steam calls are written. Deferring it means every early SDK call lands in the wrong layer.

Top recommendation

Candidate 1 — Deepen PhaseSystem Strong

The win/loss/lives logic lives in three places simultaneously — PhaseSystem, BattleSystem.compute_result(), and Battle.gd. PhaseSystem is the right home for all of it: it already owns phase transitions and is the pure-function surface every battle outcome should pass through. Pulling the domain rules out of Battle.gd restores the scene boundary, eliminates the duplication, and gives PhaseSystem's test suite full coverage of every match outcome. It's also the lowest-risk refactor: Battle.gd becomes a pure renderer with no domain knowledge, which is exactly what the architecture intends.

After this lands, tackle Candidate 2 (drag-drop validation) — it fixes the most widespread scene→state violation and completes the ShopSystem.transfer() deepening that was started in the previous session.
