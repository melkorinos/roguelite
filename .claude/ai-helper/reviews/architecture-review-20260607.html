1 · Collapse the Forge surface into attempt / preview

Strong
in-process domain: Forge

systems/ForgeSystem.gd · scenes/screens/Shop.gd · scenes/slots/ForgeSlot.gd

before — wide, shallow surface

forge → state
forge_from_bench → {state,outcome,level_mismatch}
level_up → state
level_up_grid → state
move_to_forge_slot → state
forge_quick_slot → state
forge_quick_slot_from_grid → state
remove_from_forge_slot → state
preview / preview_bench → String

9 functions, 3 return shapes. The scene must know which to call and how to read each.

after — deep, two-verb interface

attempt(state, op) → {state, outcome}
preview(state, op) → String

op ∈ { bench, quick_slot, move_to_slot, remove, level_up } · all the bench/slot plumbing greyed out inside

Problem. Nine forge functions with three return shapes; the scene carries the mechanics.

Solution. One attempt(state, op) + one preview(state, op) over an op vocabulary; the slot plumbing moves inside.

  • leverage: one interface, every forge path
  • locality: the two incoming loop concerns land here
  • interface shrinks; implementation absorbs the plumbing
  • tests hit one verb, not nine
Both queued loop concerns — "Forge requires Level-≥2 inputs" and "recipe discoverability" — edit Forge behaviour. Deepening first concentrates that change in one module instead of nine entry points.

2 · Give drop-validation the same seam as drop-apply

Worth exploring
in-process domain: Shop / Battlegrid

scenes/slots/{InventorySlot,BattleSlot,ShopItemTile,SellZone,ForgeSlot}.gd · systems/ShopSystem.gd

before — validation leaks into 5 slots

flowchart TD
  IS[InventorySlot._can_drop_data] -->|builds {zone,slot}| CT[ShopSystem.can_transfer]
  BS[BattleSlot._can_drop_data] -->|builds {zone,slot}| CT
  ST[ShopItemTile._can_drop_data] -.rule inline.-> X1[ ]
  SZ[SellZone._can_drop_data] -.rule inline.-> X2[ ]
  FS[ForgeSlot._can_drop_data] -.rule inline.-> X3[ ]
  classDef leak stroke:#dc2626,stroke-width:2px;

  style X1 fill:#fff,stroke:#fff
  style X2 fill:#fff,stroke:#fff
  style X3 fill:#fff,stroke:#fff

Apply already flows through resolve_drop; validation does not — a one-sided seam.

after — one drop seam, both sides

flowchart TD
  IS[InventorySlot] --> CR
  BS[BattleSlot] --> CR
  ST[ShopItemTile] --> CR
  SZ[SellZone] --> CR
  FS[ForgeSlot] --> CR
  CR[["ShopSystem.can_resolve(from,to)"]] --- RD[["ShopSystem.resolve_drop(from,to)"]]
  classDef deep fill:#0f172a,color:#e2e8f0,stroke:#334155;
  class CR,RD deep

Slots ask one question; the rule has one home next to its apply twin.

Problem. Drop legality is re-derived in five slot scripts; only the apply path is consolidated.

Solution. Add can_resolve(state, from, to) beside resolve_drop; slots build a location and ask once.

  • locality: one rule, not five copies
  • leverage: can & apply share the seam
  • slots become thin adapters
  • the rule is testable without a SceneTree

3 · Make the status-modifier seam typed, not stringly

Worth exploring
in-process domain: Status

data/EffectRegistry.gd · systems/StatusSystem.gd · systems/AbilitySystem.gd (set_status_field) · data/AbilityData.gd

before — one field, three scattered places

AbilityData
writes set_status_field("burn","tick_damage_bonus",1)
↓ string key, no checker
EffectRegistry.status_shape
declares the field exists (informally)
↓ string key, no checker
StatusSystem.tick
reads dict["tick_damage_bonus"] at the calc site

after — registry owns each modifier end-to-end

EffectRegistry: each modifier = {name, default, applies_at}

writer + reader both resolve through the registry entry; adding a modifier is one declaration, not a three-file hunt.

Problem. A modifier's writer, declaration, and reader sit in three files joined only by a string; nothing fails when they drift.

Solution. Let EffectRegistry declare each modifier (name, default, where it's read), and route set_status_field + calc sites through it.

  • locality: one declaration per modifier
  • a typo'd field name can be caught
  • the modifier set is discoverable in one place
  • leverage: future status tuning has one home
Lower urgency: the status engine is stable and the ×1 tuning placeholders just landed in TuningData. Worth it if status modifiers keep multiplying (T4, new keywords).

4 · Concentrate the GameState shape

Speculative
in-process domain: Run / GameState

data/GameState.gd · data/CombatState.gd · every systems/*.gd and scenes/*.gd reader

before — the shape has no single home

GameState.create() — ~30 keys
CombatState.reset() — per-combat keys
readers everywhere: state["key"] as T
to_battle / advance_round add keys ad-hoc

Interface to "the state" = memorise the string keys and their types. Knowledge is everywhere.

after — typed accessors, one declared shape

GameState.player_hp(s) · .run_discoveries(s) · …
shape + types declared once; readers stop guessing keys

Problem. The run-state shape is split across three writers and read by raw string keys in every module — no locality for "what is the state."

Solution. A thin typed accessor module over the dict (keep the dict), so the shape and its types live in one place.

  • locality: shape declared once
  • navigability: keys are discoverable, not folklore
  • typos surface at the accessor, not at runtime
  • keeps the pure-dict, return-new-dict model
⚠ Brushes the settled "plain Dictionary, systems return a new dict" decision (memory.md). Accessors keep the dict, so it's compatible — but only worth doing if key-drift bugs start biting. Reopen deliberately, don't drift into it.

Top recommendation

Start with #1 — collapse the Forge surface.

It's the one deepening that pays off immediately: the two queued loop concerns (Level-gated forge inputs, recipe discoverability) both change Forge behaviour. Unifying the nine entry points into attempt / preview first means that work — and its tests — land in one deep module instead of being smeared across the scene and nine functions. #2 is the clean follow-up; #3 and #4 wait for their pain to show up.
